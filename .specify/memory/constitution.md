# auditd-ebpf Constitution

## Core Principles

### I. Rust 与 Aya 优先

项目的用户态组件和 eBPF 程序 MUST 使用 Rust 实现，并以 Aya 作为 eBPF 加载、
映射访问和程序挂载框架。工作区 MUST 至少隔离用户态、eBPF 侧和双方共享的事件类型，
共享类型不得依赖用户态专属库。引入 C、libbpf、BCC 或其他 eBPF 框架 MUST 在设计文档中
证明 Aya 无法满足需求，并记录替代方案、构建影响和移除计划。

理由：统一 Rust 类型系统和工具链可以减少跨语言 ABI、构建链及内存安全风险，同时保留
Aya 对内核 eBPF 能力的直接控制。

### II. 内核侧最小化与验证器安全

eBPF 程序 MUST 只完成事件筛选、必要字段采集、轻量关联和投递；规则解释、格式化、
持久化及网络输出 MUST 位于用户态。所有内核侧循环、内存访问、栈使用和映射容量 MUST
具有明确上界。`unsafe`、指针运算、布局假设及验证器规避逻辑 MUST 附带中文安全注释，
说明前置条件、边界和失败后果。内核热路径不得 panic，不得执行无界字符串处理，也不得
为便利采集未被需求使用的数据。

理由：内核侧故障影响整机稳定性，最小程序更容易通过验证器、兼容不同内核并控制开销。

### III. 稳定事件契约与丢失可见

内核态与用户态之间的事件结构 MUST 使用固定宽度类型、显式布局、版本号和长度字段。
任何字段语义、布局或枚举值变更 MUST 提供兼容性说明和契约测试；不兼容变更 MUST 提升
事件主版本。事件通道 MUST 选择 Aya 支持的映射机制，并记录容量与背压依据。缓冲区满、
用户态消费落后、解析失败和不支持版本 MUST 通过计数器或结构化日志显式暴露，禁止静默
丢弃。无法可靠获取的字段 MUST 表示为缺失或未知，不得伪造默认值。

理由：审计系统的可信度取决于事件含义稳定以及数据缺口可被发现。

### IV. 最小权限、受控原样审计与风险接受

系统 MUST 仅申请加载和运行所必需的 Linux capabilities、挂载点及文件权限；完成 eBPF
加载后，用户态进程 MUST 在平台允许时丢弃不再需要的权限。每项采集字段 MUST 可追溯到
明确需求。匹配 exec 审计规则时，系统 MUST 默认在事件长度上限内原样输出完整命令行参数，
不得默认脱敏、猜测或删除参数；发生长度截断时 MUST 明确标记。系统 MUST 提供关闭 argv
输出的全局或规则级控制，但关闭行为不得被表述为默认安全保证。

由于 argv 可能包含凭据、令牌、密钥和个人数据，生产部署 MUST 在启用前记录风险接受，至少
包含责任人、用途、获准读取主体、日志目的地、传输保护、文件或 journal 访问策略、保留期和
事件响应要求。journal、rsyslog、本地文件和远端接收端 MUST 仅允许获准审计管理员读取；
远端传输 MUST 使用经认证的加密通道。未完成风险接受或无法验证访问控制时，不得宣称部署
符合生产安全门禁。规则或配置输入 MUST 经过验证，并对资源上限、路径和格式实施约束。

理由：原样 argv 提高取证完整性，但把敏感数据风险转移到日志访问、传输、保留和责任治理；
该取舍必须显式接受并通过强访问控制约束，而不是以不可验证的自动脱敏制造安全假设。

### V. 测试先行与真实内核验证

所有可测试行为 MUST 先定义验收场景和失败测试，再实现通过测试的最小代码。共享事件类型、
序列化、规则和过滤逻辑 MUST 具有单元测试；内核态到用户态的数据路径 MUST 具有契约测试；
加载、挂载、事件触发、丢失统计和关闭清理 MUST 在受支持的真实 Linux 内核或等价 CI
环境执行集成测试。每项功能 MUST 明确最低内核版本、架构范围以及无法在普通测试环境运行
的特权测试命令。缺少特权环境时可以跳过执行，但不得删除测试或宣称已验证。

理由：仅编译成功不能证明 eBPF 程序可被验证器接受，也不能证明事件语义正确。

### VI. 可观测性能与受控降级

每个功能规格 MUST 定义可测量的吞吐、延迟、CPU、内存、映射容量或事件丢失目标中适用的
项目。用户态 MUST 提供结构化运行日志和关键指标，至少覆盖程序加载状态、挂载状态、处理
事件数、丢失数、解析失败数和输出失败数。热路径变更 MUST 提供基准或前后对比。达到资源
上限时系统 MUST 按文档策略降级、采样、拒绝配置或停止，禁止无限增长和静默失效。

理由：审计代理必须长期运行，性能退化和观测盲区都可能演变为安全缺口。

### VII. 中文文档、注释与决策可追溯

规格、计划、任务、运行手册和面向维护者的文档 MUST 使用中文。公共 API、事件字段、
复杂算法、`unsafe` 块、内核兼容处理和非显然约束 MUST 提供准确的中文文档或注释；注释
MUST 解释“为什么”和安全边界，不得机械复述代码。设计可参考 Aya、Falco 等成熟开源项目，
但 MUST 优先查阅官方文档或源代码，在 `research.md` 记录参考项目、采用或拒绝的方案、
许可证影响和本项目差异，禁止无来源复制。

理由：中文可维护性是本项目的明确交付要求，而可追溯决策可避免盲目照搬复杂架构。

## 技术与架构约束

- 项目 MUST 使用 Cargo workspace；建议采用 `auditd-ebpf`（用户态）、`auditd-ebpf-ebpf`
  （内核态）和 `auditd-ebpf-common`（共享 ABI）等职责清晰的 crate 划分。
- eBPF 目标、最低 Rust 工具链、最低 Linux 内核版本、支持架构和所需 capabilities MUST
  在实现计划与快速开始文档中固定；升级 MUST 经过兼容性验证。
- 用户态负责配置、规则、丰富化、聚合、输出和生命周期管理；内核态不得实现可在用户态
  完成的策略引擎。新增 hook 类型 MUST 说明选择 tracepoint、kprobe、LSM、cgroup 等机制
  的理由及回退方案。
- 事件结构 MUST 保持 `no_std` 兼容；跨边界类型不得直接包含指针、动态容器、Rust 默认
  布局枚举或平台宽度整数。
- 依赖 MUST 最小化并锁定；新增依赖 MUST 检查维护状态、许可证、安全风险和 `no_std`
  适用性。生产代码不得依赖未记录来源的补丁或复制代码。
- 匹配 exec 规则时默认原样输出 argv 是项目明确的审计契约；生产日志 MUST 实施最小读取权限、
  经认证加密传输、受控保留和书面风险接受。诊断日志不得重复输出 argv，其他敏感字段不得在
  未被规则请求时额外采集。日志 MUST 可配置级别，并避免在热路径生成无界高基数内容。

## 开发流程与质量门禁

1. 每项功能依次产出 `spec.md`、`plan.md`、必要的 `research.md`/契约以及 `tasks.md`；
   未通过宪章检查不得开始实现。
2. 设计 eBPF hook、事件传输、内核兼容、权限模型或规则引擎时 MUST 调研 Aya 官方资料和
   相关成熟开源实现，并将结论写入设计工件。
3. 每个任务或逻辑组完成后 MUST 运行适用的格式化、静态检查和测试。最低门禁为
   `cargo fmt --check`、严格 Clippy、用户态测试、共享 ABI 测试以及可用环境中的特权集成测试。
4. 每个里程碑 MUST 在工作树通过该里程碑门禁后创建独立 Git commit；提交信息 MUST
   概括交付结果。禁止把多个未验证里程碑压入同一提交，也禁止提交密钥、构建产物或采集数据。
5. 代码评审 MUST 核对验证器安全、事件兼容、权限、argv 原样输出边界、日志访问控制、
   风险接受、丢失可见性、性能目标、中文注释和测试证据。任何例外 MUST 在计划的复杂度
   跟踪表中记录理由、替代方案和偿还条件。
6. 发布前 MUST 在声明支持的内核/架构矩阵上验证加载、挂载、事件语义、压力、关闭清理和
   升级兼容，并提供可复现的快速开始与回滚说明。

## Governance

本宪章优先于项目中的其他流程文档、临时约定和个人偏好。修改宪章 MUST 提交包含动机、
影响分析、迁移步骤和模板同步结果的变更，并由维护者评审通过。版本遵循语义化规则：删除或
重新定义既有原则、造成治理不兼容时提升 MAJOR；新增原则或实质扩展约束时提升 MINOR；
不改变含义的澄清提升 PATCH。

所有规格、计划、任务和代码评审 MUST 显式验证宪章合规。无法立即合规的变更 MUST 在合并前
记录限期整改项及责任范围；违反内核安全、权限最小化、事件可信度或敏感数据保护的变更不得
以例外方式合并。每个发布里程碑和每次宪章修订后 MUST 复查依赖模板与运行文档。

原样 argv 的风险接受只确认已知数据暴露风险，不得用于豁免最小权限、访问控制、加密传输、
保留期或事件响应要求。生产发布评审 MUST 验证风险接受仍有效且与实际日志链路一致。
