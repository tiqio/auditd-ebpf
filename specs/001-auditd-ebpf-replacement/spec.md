# Feature Specification: auditd-ebpf 替代与性能验证

**Feature Branch**: `main`

**Created**: 2026-08-10

**Status**: Draft

**Input**: User description: "实现 Linux auditd 的替代品 auditd-ebpf，读取现有审计规则，
输出日志到标准输出以便 journalctl 管理并由 rsyslog 转发，同时定量证明相对 auditd 的性能提升。"

## Clarifications

### Session 2026-08-10

- Q: 首版规则兼容范围是什么？ → A: 仅支持常用规则子集。
- Q: 标准输出的审计事件采用什么格式？ → A: 传统 audit 风格的单行 key=value 文本。
- Q: 高负载或标准输出阻塞时如何处理？ → A: Ring buffer 保存事件，每 CPU 计数器记录丢失；
  用户态队列动态扩容至硬上限，超限后丢弃新事件并标记降级。
- Q: 是否采集进程启动参数？ → A: exec 规则命中时默认不脱敏、原样记录完整命令行参数；
  生产部署通过访问控制和书面风险接受治理该风险。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 使用现有审计规则采集事件 (Priority: P1)

Linux 系统管理员希望停用传统 auditd 后，继续使用已有的审计规则文件启动服务，采集规则
命中的系统调用、进程和文件访问事件，而不必重新学习另一套基础规则表达方式。

**Why this priority**: 规则兼容和事件可信度是替代 auditd 的核心价值；如果无法复用规则或
准确产出事件，日志集成与性能优势都没有意义。

**Independent Test**: 使用声明兼容的规则语料启动服务，执行一组确定性的命令、进程和文件
访问操作，验证每条规则均生成预期事件、key 和身份字段，并验证未命中操作不会产生误报。

**Acceptance Scenarios**:

1. **Given** 存在有效的 syscall 过滤规则，**When** 对应系统调用由匹配主体执行，
   **Then** 系统输出包含规则 key、主体身份、进程信息、调用结果和时间信息的审计事件。
2. **Given** 存在文件或目录监控规则，**When** 匹配路径发生声明权限类型的访问，
   **Then** 系统输出可关联到规则和目标路径的事件。
3. **Given** 规则包含不受支持的动作、字段或操作符，**When** 服务加载规则，
   **Then** 服务逐行报告文件名、行号和原因，并拒绝以部分规则静默启动。
4. **Given** 规则文件包含空行、注释和多个规则文件，**When** 服务启动，
   **Then** 系统按确定顺序组合规则且不把注释解释为规则。

---

### User Story 2 - 通过系统日志链路管理审计记录 (Priority: P2)

系统管理员希望服务把审计事件输出到进程标准输出，由服务管理器收集，并能够使用
`journalctl` 查询，也能够通过 rsyslog 的现有配置写入本地或远端日志目的地。

**Why this priority**: 复用主流 Linux 服务日志链路可以避免服务自行管理日志文件、轮转和
传输，降低部署与运维成本。

**Independent Test**: 启动服务并触发带唯一 key 的审计事件，分别从服务日志查询结果和
rsyslog 测试目的地检索该 key，确认记录完整、仅出现预期次数且能区分审计事件与诊断信息。

**Acceptance Scenarios**:

1. **Given** 服务由支持标准输出采集的服务管理器启动，**When** 产生审计事件，
   **Then** 管理员能按服务标识、时间范围和规则 key 查询到完整记录。
2. **Given** rsyslog 已配置接收该服务记录，**When** 产生审计事件，
   **Then** 同一事件能被转发到配置目的地，并保留事件标识和全部审计字段。
3. **Given** 下游日志目的地暂时不可用，**When** 事件持续产生，
   **Then** 系统暴露输出失败或积压状态，不把失败误报为成功交付。
4. **Given** 服务发生加载、规则解析或运行错误，**When** 管理员查看服务日志，
   **Then** 诊断记录与审计事件可以被稳定区分并包含可操作原因。

---

### User Story 3 - 获得可复现的性能提升证据 (Priority: P3)

性能工程师希望在相同硬件、内核、规则和工作负载下，对传统 auditd 与本系统进行公平对照，
获得事件正确性、业务负载影响、资源占用和丢失情况的量化结果，而不是仅凭架构推断性能更好。

**Why this priority**: “性能更高”是本项目的核心主张，必须以可复现数据证明，但其前提是
前两个故事已建立正确的采集与输出路径。

**Independent Test**: 在隔离主机上分别运行传统方案和本系统，对 syscall 密集、文件监控
密集及混合负载各执行预热和至少 5 次有效测量，生成包含原始数据、环境、规则、命令、
统计方法和结论的报告，并由另一名维护者复现。

**Acceptance Scenarios**:

1. **Given** 两种方案使用语义等价规则和相同工作负载，**When** 执行基准，
   **Then** 报告同时给出工作负载吞吐与延迟、审计进程 CPU 与内存、事件数和丢失数。
2. **Given** 两种方案输出格式不同，**When** 比较事件正确性，
   **Then** 先规范化非确定字段，再按工作负载预期事件和规则 key 检查缺失、重复及误报。
3. **Given** 任一性能目标未达成或正确性不等价，**When** 生成报告，
   **Then** 报告明确标记未通过，且发布材料不得宣称已获得性能提升。
4. **Given** 环境、规则、负载或统计方法发生变化，**When** 比较新旧报告，
   **Then** 变更被显式记录，避免把不可比结果合并为趋势。

### Edge Cases

- 规则文件不存在、不可读、为空、包含超长行或包含重复/互相冲突规则时如何处理？
- 32 位与 64 位系统调用架构规则并存，或规则引用当前架构不存在的系统调用时如何处理？
- 被监控路径在启动时不存在，或运行中发生重命名、删除、重新挂载时如何报告？
- 极短生命周期进程在事件被消费前退出时，哪些身份和路径字段仍可被可信获取？
- 事件速率超过缓冲能力、标准输出阻塞或日志管理器限速时，如何暴露丢失和积压？
- 规则重载期间有并发事件时，事件如何关联到生效的规则版本？
- 服务异常退出、被强制终止或主机关闭时，如何清理采集状态并说明未刷新的事件？
- rsyslog 重启、断网、磁盘写满或远端拒收时，如何区分本服务成功输出与最终转发失败？

## Requirements *(mandatory)*

### Scope

- 首版范围包括规则驱动的系统调用、进程执行、文件和目录访问审计，以及相关主体、进程、
  路径、调用结果和规则 key 字段。
- 首版规则子集限定为 syscall 选择、arch、uid/gid、成功或失败结果、path/dir、perm 和 key；
  具体支持的字段变体与操作符 MUST 在版本化兼容矩阵中逐项列出。
- 首版不承诺兼容传统二进制审计日志、`ausearch`/`aureport` 文件接口、远端管理协议，
  也不支持首版子集以外的控制指令、排除列表、LSM 或用户态自报审计消息。
- 发行版本 MUST 随附明确的规则兼容矩阵；未列为支持的语法不得被静默接受。

### Functional Requirements

- **FR-001**: 系统 MUST 从默认规则目录读取按文件名确定排序的规则文件；当默认规则目录
  没有可用规则时，MUST 支持读取单一合并规则文件作为回退。
- **FR-002**: 系统 MUST 识别空行、注释，以及首版规则子集中的 syscall、arch、uid/gid、
  成功或失败结果、path/dir、perm 和 key；兼容矩阵未声明的字段、操作符和指令均视为不支持。
- **FR-003**: 系统 MUST 在启动前验证全部规则，并为每个无效或不支持规则报告文件、行号、
  原始规则摘要和原因；默认行为 MUST 是拒绝部分生效。
- **FR-004**: 系统 MUST 为每次规则加载或重载分配可识别版本，并使每个输出事件可追溯到
  产生该事件的规则版本和规则 key。
- **FR-005**: 系统 MUST 在无需重启主机的情况下重新加载有效规则；重载失败时 MUST 保留
  上一完整有效版本，并明确报告失败。
- **FR-006**: 系统 MUST 对每个匹配操作生成传统 audit 风格的单行 `key=value` 审计记录，
  并提供稳定事件标识，以便日志链路去重和关联。
- **FR-007**: 审计事件 MUST 在字段可可靠获得时包含时间、主机、规则 key、规则版本、
  进程与父进程标识、用户身份、可执行对象、系统调用或操作、目标路径、结果和退出状态。
- **FR-007a**: exec 规则命中时，进程启动事件 MUST 默认在长度上限内不脱敏、原样记录完整
  命令行参数；达到单参数或事件总长度上限时，MUST 显式标记截断位置和原始参数数量，不得
  把截断内容表示为完整值。系统 MUST 提供全局或规则级关闭 argv 输出的控制。
- **FR-008**: 无法可靠获取的字段 MUST 明确表示为未知或缺失，不得填充可能误导分析的值。
- **FR-009**: 系统 MUST 将审计事件写入标准输出，并将生命周期与诊断记录写入可区分的
  日志流或记录类别；系统不得要求自行管理专用日志文件才能正常运行。
- **FR-010**: 每条输出记录 MUST 能被服务日志查询链路保持为完整单元，并能被 rsyslog
  依据稳定服务标识或记录属性选择和转发。
- **FR-010a**: 审计字段 MUST 使用稳定名称和确定顺序；空格、引号、换行、控制字符及非打印
  字节 MUST 采用有文档且可逆的转义，任何字段内容不得生成额外日志行或伪造字段边界。
- **FR-011**: 系统 MUST 提供处理事件数、成功输出数、解析失败数、规则版本、输出失败数和
  当前健康状态；事件缓冲预留失败与丢失数 MUST 由每 CPU 计数器记录并可聚合查询。
- **FR-012**: 内核事件缓冲 MUST 保存完整事件且保持有界；用户态输出队列 MUST 能根据积压
  动态扩容至配置的硬上限。达到任一容量上限后，系统 MUST 丢弃新事件、增加对应丢失计数并
  立即标记为降级，禁止阻塞被审计业务、无限增长或静默丢弃。
- **FR-013**: 系统 MUST 支持干运行规则验证，使管理员无需启用采集即可检查规则兼容性。
- **FR-014**: 系统 MUST 提供可复现的对照基准流程，固定环境信息、规则集、负载、预热、
  测量次数、原始结果和统计摘要。
- **FR-015**: 基准流程 MUST 在比较性能前验证两种方案对确定性测试负载的事件覆盖等价性；
  存在未解释缺失、重复或误报时，性能结果 MUST 判定为无效。
- **FR-016**: 发布材料中的性能结论 MUST 可追溯到版本化报告，不得选择性省略未达标负载、
  事件丢失、环境差异或统计波动。

### Security & Audit Data Requirements *(mandatory)*

- **SR-001**: 系统 MUST 明确启动、加载、运行和关闭各阶段所需权限，并在不再需要时释放
  多余权限；服务不得以方便为由长期保留未使用的高权限。
- **SR-002**: 规则文件和运行配置 MUST 来自受信任路径；文件所有权或写权限不安全时，
  系统 MUST 拒绝加载并给出原因。
- **SR-003**: 匹配 exec 规则时系统 MUST 默认原样输出完整命令行参数，不执行默认脱敏、猜测
  或删除。生产部署 MUST 明确提示参数可能含密码、令牌、密钥和个人数据，并记录责任人、用途、
  获准读取主体、日志目的地、传输保护、journal/文件访问策略、保留期和事件响应要求。
- **SR-003a**: journal、rsyslog、本地文件和远端接收端 MUST 只允许获准审计管理员读取；远端
  转发 MUST 使用经认证的加密通道。风险接受缺失或访问控制无法验证时，生产就绪检查 MUST
  失败，但测试环境可以在明确标记为非生产后运行。
- **SR-004**: 事件和诊断记录 MUST 防止换行、控制字符或字段内容破坏记录边界或伪造日志。
- **SR-005**: 系统 MUST 定义规则数量、单条规则长度、路径长度、缓冲区和输出队列上限，
  对超限输入给出确定且可审计的结果。
- **SR-006**: 系统 MUST 在自身加载失败、采集程序失效或规则未生效时进入不健康状态；发生
  任意事件丢失时 MUST 立即进入可观测的降级状态，并持续保留累计与分 CPU 丢失计数。
- **SR-007**: 系统 MUST 记录性能测试使用的权限、数据范围和清理步骤，避免基准数据泄露
  真实生产敏感信息。

### Key Entities *(include if feature involves data)*

- **规则源**: 一个规则文件及其可信路径、加载顺序、内容摘要和验证结果。
- **审计规则**: 规范化后的动作、过滤条件、系统调用或路径选择、权限掩码及规则 key。
- **规则版本**: 一次完整有效的规则集合，包含版本标识、来源摘要、生效时间和替代关系。
- **审计事件**: 一次被规则命中的操作及其主体、进程、目标、结果、规则关联和完整性状态。
- **运行健康状态**: 采集、解析、缓冲、输出和规则加载各环节的状态与累计计数。
- **基准场景**: 固定的环境、规则集、工作负载、预期事件集合和测量方法。
- **基准结果**: 单次或汇总测量的吞吐、延迟、CPU、内存、事件正确性、丢失率和结论。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 声明支持的规则兼容语料中 100% 的规则能通过干运行验证并产生预期规范化结果；
  不支持语法 100% 被逐行识别，且不存在静默忽略。
- **SC-002**: 对确定性正确性负载，规范化后预期审计事件覆盖率为 100%，未解释重复和误报为 0；
  进程启动事件包含完整测试参数或明确截断标记；压力负载下任何丢失均能与系统报告的丢失
  计数对应。
- **SC-003**: 管理员能在触发测试事件后 10 秒内通过服务日志查询找到记录，并能在配置的
  rsyslog 测试目的地中使用事件标识检索到相同事件。
- **SC-004**: 无效规则、权限错误和采集失效均在 10 秒内形成可操作的不健康状态；首次缓冲
  丢失或输出阻塞导致的丢弃在 10 秒内形成降级状态和非零丢失计数，且不会被误判为正常。
- **SC-005**: 在 syscall 密集、文件监控密集和混合三类等价负载中，相比传统方案，
  本系统的审计组件 CPU 中位数每类均至少降低 20%，且工作负载吞吐任一类别不得下降超过 2%。
- **SC-006**: 三类等价负载中至少两类的工作负载吞吐中位数提升 10% 以上，或 p95 延迟降低
  10% 以上；所有对比必须同时满足 SC-002 的正确性要求。
- **SC-007**: 每个基准场景至少有 5 次有效测量，报告公布全部有效样本、离散程度、环境、
  规则、负载和复现命令；另一名维护者可在同等环境复现方向一致的结论。
- **SC-008**: 持续 24 小时的稳定性测试中，服务内存无无界增长，所有事件丢失、解析失败和
  输出失败均有计数，服务停止后不遗留活动采集状态。
- **SC-009**: 生产就绪验证能 100% 检出缺失风险接受、journal/文件权限过宽、未加密远端转发
  或未定义保留期，并阻止将该部署标记为生产合规。

## Compatibility & Privileged Testing *(mandatory for eBPF changes)*

- **Minimum Kernel**: 首版计划阶段必须根据所需采集能力确定最低 Linux 内核版本，并在低于
  该版本时启动失败且说明缺失能力，禁止以未声明的部分功能运行。
- **Architectures**: 首版以 x86_64 为必测架构；其他架构只有在规则语义、事件字段和特权
  集成测试全部通过后才能列为支持。
- **Attach Mechanism**: 具体采集点由计划阶段基于稳定性、字段可得性、开销和回退能力选择；
  每类规则必须具有从规则语义到采集点的可追溯映射。
- **Fallback Behavior**: 所需内核能力或采集点不可用时，对受影响规则必须拒绝加载或将服务
  标记为不健康，禁止静默降低审计覆盖。
- **Privileged Test**: 测试必须覆盖规则加载、重新加载、挂载、确定性事件触发、高负载丢失、
  异常停止清理以及声明支持的最低和代表性较新内核。

## Assumptions

- 项目治理已固定实现语言和采集框架；具体 crate、采集点、事件传输和代码结构在计划阶段决定，
  本规格只定义用户可观察行为和验收结果。
- 首版面向使用 systemd 管理服务并提供标准 Linux 审计规则文件的服务器，传统 auditd 在启用
  本服务前停止，以避免重复采集和结果混淆。
- 现有 rsyslog 部署负责最终路由、远端重试、磁盘队列、轮转和保留；本服务负责提供可可靠
  分流的完整记录及自身输出成功/失败状态，不声称能感知每个远端目的地的最终持久化结果。
- exec 规则命中后的 argv 默认原样输出且不脱敏；生产运维方接受该取证完整性与敏感数据暴露
  取舍，并负责限制 journal/rsyslog/文件/远端接收端读取权限、加密传输和执行保留策略。
- 性能基线使用同一主机、同一内核、同一隔离设置、同一语义规则和同一工作负载顺序随机化，
  不使用跨硬件或跨内核结果证明相对提升。
- 兼容范围以版本化规则语料和矩阵为准，而不是笼统宣称支持全部历史 audit 子系统语法。
- 默认采用失败关闭策略：规则无法完整验证、关键采集能力缺失或规则重载失败时，不以不完整的
  新配置继续运行；重载场景可保留上一完整有效规则版本。
